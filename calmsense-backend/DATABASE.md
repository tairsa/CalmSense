# CalmSense Database Guide

This document explains the CalmSense SQL schema: every table, its columns, keys,
indexes, how the tables relate to each other, and answers to questions you might
be asked about it.

The canonical schema lives in [`supabase_schema.sql`](supabase_schema.sql). The
Pydantic request models that map onto these tables live in
[`models.py`](models.py). When Supabase credentials aren't configured, the
backend falls back to local JSON files under `calmsense-backend/data/` with the
same field shapes (see [`storage.py`](storage.py)).

---

## Big picture

There are **three tables**, all in the `public` schema:

| Table            | What it holds                                              | Written when                                          |
| ---------------- | --------------------------------------------------------- | ----------------------------------------------------- |
| `sensor_data`    | Raw per-sample vitals readings streamed from the phone    | Every sensor poll (`POST /api/v1/sensor-data`)        |
| `panic_feedback` | Labeled hit/miss training signals (ground truth)          | User confirms/rejects a detection (`POST .../panic-feedback`) |
| `panic_reports`  | Journaled, post-event panic entries (questionnaire + GPS) | User fills the questionnaire (`POST .../panic-reports`) |

They are **logically related by `user_id`** but there are **no enforced foreign
keys** between them (see the "connections" section below for why).

### Entity-relationship sketch

```
                         user_id (text, not enforced as FK)
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                             │
┌───────────────┐          ┌──────────────────┐          ┌────────────────┐
│  sensor_data  │          │  panic_feedback  │          │  panic_reports │
│  (telemetry)  │          │  (labels / truth)│          │  (journal)     │
├───────────────┤          ├──────────────────┤          ├────────────────┤
│ id  PK        │          │ id  PK           │          │ id  PK         │
│ user_id  idx  │          │ user_id  idx     │          │ user_id  idx   │
│ vitals...     │          │ was_panic        │          │ severity       │
│ timestamp     │          │ severity         │          │ symptoms jsonb │
│ created_at    │          │ model_probability│          │ lat/long       │
└───────────────┘          │ vitals snapshot  │          │ timestamp idx  │
                           └──────────────────┘          └────────────────┘
```

Each row in every table belongs to one user. A panic event typically produces a
burst of `sensor_data` rows, then one `panic_feedback` row (the label), and
optionally one `panic_reports` row (the journal entry) — but nothing in the DB
links those specific rows together. They're correlated after the fact by
`user_id` + `timestamp`.

## Table 1: `sensor_data`

Raw vitals telemetry. One row per sensor poll from the phone.

| Column                     | Type               | Null? | Notes                                          |
| -------------------------- | ------------------ | ----- | ---------------------------------------------- |
| `id`                       | `bigint` identity  | no    | **Primary key**, auto-generated by the DB      |
| `user_id`                  | `text`             | no    | Owner of the reading                           |
| `panic_attack_detection`   | `boolean`          | no    | Did the on-device model fire on this sample?   |
| `current_hr`               | `double precision` | yes   | Heart rate, BPM                                |
| `current_hrv`              | `double precision` | yes   | Heart-rate variability, ms (often null today)  |
| `current_motion_intensity` | `double precision` | yes   | Motion RMS, ~0.0–1.0                            |
| `timestamp`                | `timestamptz`      | yes   | Event time; server auto-fills UTC if omitted   |
| `created_at`               | `timestamptz`      | no    | DB insert time, defaults to `now()`            |

**Keys & indexes**

- Primary key: `id`
- Index `sensor_data_user_id_idx` on `(user_id)` — fast per-user history lookups.

## Table 2: `panic_feedback`

Labeled training signal — the ground truth used to retrain the classifier and to
compute the per-user hit/miss (confusion) matrix.

| Column                     | Type               | Null? | Notes                                                   |
| -------------------------- | ------------------ | ----- | ------------------------------------------------------- |
| `id`                       | `bigint` identity  | no    | **Primary key**                                         |
| `user_id`                  | `text`             | no    | Owner                                                   |
| `was_panic`                | `boolean`          | no    | Ground truth from the user                              |
| `severity`                 | `smallint`         | yes   | `CHECK (severity between 1 and 10)`; only when panic    |
| `detected_by_model`        | `boolean`          | no    | `true` = detection path, `false` = manual log           |
| `current_hr`               | `double precision` | yes   | Vitals snapshot at the moment                           |
| `current_hrv`              | `double precision` | yes   |                                                         |
| `current_motion_intensity` | `double precision` | yes   |                                                         |
| `model_probability`        | `double precision` | yes   | `p(panic)` the on-device model emitted                  |
| `timestamp`                | `timestamptz`      | yes   | Event time; server auto-fills if omitted                |
| `created_at`               | `timestamptz`      | no    | DB insert time                                          |

**Keys & indexes**

- Primary key: `id`
- Index `panic_feedback_user_id_idx` on `(user_id)`

**How the label combinations map to outcomes**

| `detected_by_model` | `was_panic` | Meaning            | Confusion-matrix cell |
| ------------------- | ----------- | ------------------ | --------------------- |
| `true`              | `true`      | model fired, real  | True Positive         |
| `true`              | `false`     | model fired, false | False Positive        |
| `false`             | `true`      | user logged manual | False Negative (miss) |

(A confirmed True Negative isn't logged — the absence of a detection is implicit.)

## Table 3: `panic_reports`

Journaled, post-event entries the user fills via the questionnaire. Sensitive:
contains free text and GPS.

| Column                     | Type               | Null? | Notes                                              |
| -------------------------- | ------------------ | ----- | -------------------------------------------------- |
| `id`                       | `bigint` identity  | no    | **Primary key**                                    |
| `user_id`                  | `text`             | no    | Owner                                              |
| `timestamp`                | `timestamptz`      | yes   | Event start time                                   |
| `severity`                 | `smallint`         | no    | `CHECK (between 1 and 10)` — required here          |
| `detected_by_model`        | `boolean`          | no    | Was the event auto-detected or manually logged?    |
| `feeling`                  | `text`             | yes   | Free text — "what were you feeling?"               |
| `symptoms`                 | `jsonb`            | yes   | Array of symptom chips, e.g. `["racing heart"]`    |
| `activity_before`          | `text`             | yes   | Free text                                          |
| `what_helped`              | `text`             | yes   | Free text                                          |
| `duration_minutes`         | `integer`          | yes   | `CHECK (between 0 and 1440)`                        |
| `latitude`                 | `double precision` | yes   | GPS, null if location permission denied            |
| `longitude`                | `double precision` | yes   |                                                    |
| `location_accuracy_m`      | `double precision` | yes   | Reported accuracy radius in meters                 |
| `current_hr`               | `double precision` | yes   | Vitals snapshot for therapist context              |
| `current_hrv`              | `double precision` | yes   |                                                    |
| `current_motion_intensity` | `double precision` | yes   |                                                    |
| `created_at`               | `timestamptz`      | no    | DB insert time                                     |

**Keys & indexes**

- Primary key: `id`
- Index `panic_reports_user_id_idx` on `(user_id)` — per-user report list
- Index `panic_reports_timestamp_idx` on `(timestamp)` — powers the 24h / 7d /
  30d / All time-window filters in the Reports tab

## How the tables connect

- **The only join key is `user_id`** (a free-text string the phone supplies).
- **There are no foreign-key constraints.** This is deliberate:
  - There is no `users` table — identity comes from the phone (and later, JWT),
    not from a DB row, so there is nothing to point a foreign key at.
  - The three tables are written by three independent endpoints at different
    times; an event isn't a single transaction across them.
  - Keeping them decoupled means a write to one never fails because of a missing
    parent row in another.
- **Correlation, not relation:** to reconstruct a single panic event you match
  rows across tables by `user_id` and a close `timestamp` window. The `id`
  columns are surrogate keys for each row, not cross-table links.
- **Indexing reflects the access pattern:** every table is queried "give me this
  user's rows," so every table has a `user_id` index; `panic_reports` adds a
  `timestamp` index because its UI filters by time window.

---

## Storage modes

- **Supabase (production/partner):** the backend connects with the
  **`service_role` key**, which bypasses Row Level Security. No RLS policies are
  defined. If the Android app is ever pointed at Supabase directly with the
  `anon` key, RLS **must** be enabled and policies added first.
- **Local JSON fallback (dev):** when `SUPABASE_URL`/`SUPABASE_KEY` are unset,
  rows are appended to `calmsense-backend/data/*.json` with the same field
  shapes. Good enough for single-process dev; not safe for concurrent writers.

## Likely questions & answers

**Q: Why are there no foreign keys / why isn't this normalized into a `users` table?**
A: User identity lives on the phone (`user_id` string, later a JWT subject), not
in the database, so there's no parent row to reference. The tables are written
independently by separate endpoints, and decoupling them avoids cross-table
write failures. We correlate rows by `user_id` + `timestamp` when we need to.

**Q: How do you tell which `sensor_data` rows belong to a given panic event?**
A: By `user_id` and a `timestamp` window around the `panic_feedback` /
`panic_reports` row. There's no hard link — telemetry is a continuous stream,
events are points in it.

**Q: What's the difference between `panic_feedback` and `panic_reports`?**
A: `panic_feedback` is the **machine-learning label** (was it really a panic? how
did the model do?) — small, structured, used for retraining and the hit/miss
matrix. `panic_reports` is the **human journal** — free text, symptoms, GPS,
duration — used by the user to spot patterns and review with a therapist.

**Q: Why is `severity` nullable in `panic_feedback` but required in `panic_reports`?**
A: In feedback, severity only exists when `was_panic = true` (a rejected false
alarm has no severity). A report is only created for a confirmed panic, so
severity is always present there. Note: severity is constrained to 1–10 in the
DB; in the app, severity 0 means "miss" and produces no report.

**Q: How is the confusion matrix / model accuracy computed?**
A: One query over `panic_feedback` per user, grouping on
`(detected_by_model, was_panic)` — see the label-combination table above. True
Negatives aren't stored (a non-detection is implicit).

**Q: Why is `current_hrv` so often null?**
A: The Galaxy Watch raw-sensor path streams heart rate and motion but not HRV
yet; computing HRV from beat-to-beat intervals on-device is a planned next step.

**Q: Why are GPS and free-text fields nullable?**
A: The whole questionnaire is optional and skippable, and location is only
captured if the user granted permission. The app records the event even when
everything optional is skipped.

**Q: What stops one user from reading another user's data?**
A: Today, the FastAPI server is the only thing that talks to the database (via
the `service_role` key), and it filters by `user_id`. There is no JWT auth yet —
`user_id` is trusted from the phone. Direct app-to-Supabase access would require
enabling RLS with per-user policies first. JWT auth is on the roadmap.

**Q: Are `symptoms` a separate table?**
A: No. They're stored inline as a `jsonb` array on `panic_reports` (e.g.
`["racing heart", "dizziness"]`). The set is small and only ever read back with
its parent report, so a join table would be over-engineering.

**Q: What does `id ... generated always as identity` mean and why use it over a UUID?**
A: It's an auto-incrementing surrogate primary key the database fills in; the
backend never sends `id`. It's compact and fast to index. We don't need globally
unique UUIDs because IDs are never exposed across systems or merged.

**Q: Can the same panic produce rows in all three tables?**
A: Yes — a detected panic streams `sensor_data` rows, writes one
`panic_feedback` label when confirmed, and (if the user journals) one
`panic_reports` row. They're tied together only by `user_id` + `timestamp`.
